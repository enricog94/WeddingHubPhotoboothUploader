# WeddingHub Photobooth Backend Integration Specification

> [!IMPORTANT]
> **Legacy WeddingHub contract.** This document records the previous Wedding-specific
> integration using `wedding_id` and a `wedding` verify payload. It is retained for
> history only. For all new EventHub work, the authoritative contract is
> [`docs/EVENTHUB_INTEGRATION.md`](docs/EVENTHUB_INTEGRATION.md). Do not port this schema
> unchanged into EventHub.

This document defines the formal API contract, PostgreSQL database schema, security model, and integration guidelines between the **WeddingHub Photobooth Uploader** client and the **WeddingHub Cloudflare Workers + Supabase PostgreSQL + Hyperdrive + Cloudflare R2** backend.

---

## 1. Overview & Architecture

The photobooth uploader synchronizes photos taken at wedding events to WeddingHub in real-time. It uses a **3-step decoupled upload architecture**:

```text
+------------------+         +------------------+         +------------------+
| Photobooth Client|         | WeddingHub Worker|         |  Cloudflare R2   |
+------------------+         +------------------+         +------------------+
         |                             |                            |
         | 1. POST /upload/init        |                            |
         |---------------------------->| (Checks auth & dedupe)     |
         |   {filename, sha256, size}  | (Creates upload session)   |
         |                             |                            |
         |   <200 {upload_url, id}>    |                            |
         |<----------------------------|                            |
         |                             |                            |
         | 2. PUT (Binary JPEG stream) |                            |
         |--------------------------------------------------------->|
         |   <200 OK>                                               |
         |<---------------------------------------------------------|
         |                             |                            |
         | 3. POST /upload/complete    |                            |
         |---------------------------->| (Verifies R2 object & SHA) |
         |   {upload_id, sha256}       | (Inserts media in Postgres)|
         |                             | (Sets status = approved)   |
         |   <200 {media_id}>          |                            |
         |<----------------------------|                            |
```

## 2. Security Model & Role-Based Access

1. **Zero Wedding ID Stored on Client**:
   The client machine does NOT hold or configure a `wedding_id` or admin API key. It holds only a `device_token`.
2. **Server-Side Token Hashing**:
   - The client sends `Authorization: Bearer <device_token>`.
   - The backend hashes the raw token using SHA-256 (`crypto.subtle.digest("SHA-256", ...)`).
   - Only the SHA-256 hex string is stored in the `photobooth_devices.token_hash` column.
   - Even with direct read access to the database, raw tokens cannot be recovered.
3. **Multi-Tenant Isolation**:
   - The device is permanently linked to a single `wedding_id`.
   - Storage keys are forced server-side to `weddings/<wedding_slug>/photobooth/originals/<uuid>.jpg`.
   - A device cannot write, read, complete, or probe media belonging to other weddings.
4. **Kill-Switch (Remote Revocation)**:
   - Devices have an `enabled` flag (`boolean NOT NULL DEFAULT true`).
   - Setting `enabled = false` immediately causes all API requests from that device to fail with `403 Forbidden`.
5. **Session Expiry**:
   - Upload sessions have a strict 15-minute TTL. Uncompleted sessions cannot be finalized after expiration (`410 Gone`).
6. **Row Level Security (RLS) & Grants**:
   - Worker connects via Hyperdrive using the dedicated `wedding_worker` role (`NOBYPASSRLS`).
   - Strict `GRANT` and RLS policies on `photobooth_devices` and `photobooth_upload_sessions` guarantee least privilege.

## 3. Database Schema (Supabase PostgreSQL)

### `photobooth_devices`
```sql
CREATE TABLE public.photobooth_devices (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    wedding_id bigint NOT NULL REFERENCES public.weddings(id) ON DELETE CASCADE,
    name text NOT NULL,
    token_hash text NOT NULL UNIQUE,
    enabled boolean NOT NULL DEFAULT true,
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now(),
    last_seen_at timestamptz
);

CREATE INDEX idx_photobooth_devices_token ON public.photobooth_devices(token_hash);
CREATE INDEX idx_photobooth_devices_wedding ON public.photobooth_devices(wedding_id);
```

### `photobooth_upload_sessions`
```sql
CREATE TABLE public.photobooth_upload_sessions (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    device_id bigint NOT NULL REFERENCES public.photobooth_devices(id) ON DELETE CASCADE,
    wedding_id bigint NOT NULL REFERENCES public.weddings(id) ON DELETE CASCADE,
    sha256 text NOT NULL,
    filename text NOT NULL,
    size_bytes bigint NOT NULL,
    content_type text NOT NULL,
    storage_key text NOT NULL,
    status text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'completed', 'expired')),
    created_at timestamptz NOT NULL DEFAULT now(),
    expires_at timestamptz NOT NULL,
    completed_at timestamptz,
    media_id bigint REFERENCES public.media(id) ON DELETE SET NULL
);

CREATE INDEX idx_photobooth_sessions_lookup ON public.photobooth_upload_sessions(wedding_id, sha256);
```

### Server-Side Deduplication Index on `media`
```sql
CREATE UNIQUE INDEX idx_media_photobooth_sha256
ON public.media (wedding_id, sha256)
WHERE source = 'photobooth';
```

## 4. API Endpoints Specification

### 4.1. Verify Device Token
- **Method**: `GET`
- **Path**: `/api/photobooth/verify`
- **Headers**:
  ```http
  Authorization: Bearer <device_token>
  Accept: application/json
  ```
- **Responses**:
  - `200 OK`:
    ```json
    {
      "status": "ok",
      "device": {
        "name": "Photobooth principale"
      },
      "wedding": {
        "slug": "serena-enrico-2027",
        "display_name": "Serena & Enrico"
      }
    }
    ```
  - `401 Unauthorized`: Token missing or invalid.
  - `403 Forbidden`: Device is disabled.

---

### 4.2. Initialize Upload (`init`)
- **Method**: `POST`
- **Path**: `/api/photobooth/upload/init`
- **Headers**:
  ```http
  Authorization: Bearer <device_token>
  Content-Type: application/json
  Accept: application/json
  ```
- **Request Body**:
  ```json
  {
    "filename": "IMG_20260902_220015.jpg",
    "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
    "size": 3412580,
    "content_type": "image/jpeg",
    "captured_at": "2026-09-02T22:00:15Z"
  }
  ```
- **Responses**:
  - **Upload Required (`200 OK`)**:
    ```json
    {
      "status": "upload_required",
      "upload_id": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
      "upload_url": "https://api.weddinghub.it/storage/...",
      "headers": {},
      "expires_at": "2026-09-02T22:15:15Z"
    }
    ```
  - **Deduplicated - Already Exists (`200 OK`)**:
    ```json
    {
      "status": "already_exists",
      "media_id": "105"
    }
    ```
  - `400 Bad Request`: Invalid payload, missing filename, invalid SHA-256 (not 64 hex chars), size <= 0 or > 50MB, content_type != image/jpeg.
  - `401 Unauthorized`: Invalid or missing device token.
  - `403 Forbidden`: Device is disabled.

---

### 4.3. Direct Presigned Binary Upload (`PUT`)
- **Method**: `PUT`
- **Path**: Pre-signed Cloudflare R2 PUT URL
- **Headers**:
  ```http
  Content-Type: image/jpeg
  Content-Length: <file_size>
  ```
- **Body**: Raw binary JPEG bytes.
- **Responses**:
  - `200 OK`: Binary stored in R2 bucket under `weddings/<slug>/photobooth/originals/<uuid>.jpg`.

---

### 4.4. Complete Upload (`complete`)
- **Method**: `POST`
- **Path**: `/api/photobooth/upload/complete`
- **Headers**:
  ```http
  Authorization: Bearer <device_token>
  Content-Type: application/json
  Accept: application/json
  ```
- **Request Body**:
  ```json
  {
    "upload_id": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
    "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
  }
  ```
- **Responses**:
  - `200 OK`:
    ```json
    {
      "status": "completed",
      "media_id": "106"
    }
    ```
  - `400 Bad Request`: Missing upload_id, SHA mismatch, or binary object not found in R2.
  - `401 Unauthorized`: Invalid device token.
  - `403 Forbidden`: Device disabled or unauthorized cross-device/cross-wedding access.
  - `404 Not Found`: Active session for this device not found.
  - `410 Gone`: Session expired.
